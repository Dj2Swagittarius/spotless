# Code review follow-ups — 2026-10-08

Low-severity findings from the verification pass over the review-fixes branch (origin/main..HEAD) and the first review of the AI DJ feature. Each was confirmed by an independent skeptic agent. None blocks a release; they are grouped by area. The eleven high/medium findings from the same pass were fixed on the branch.

## Security

- **Station stream proxy follows redirects, so validStreamUrl's private-IP check is bypassed by a 302** — src/app/api/stations/[id]/stream/route.ts:30
  validStreamUrl rejects loopback/RFC1918 targets, but the relay calls fetch with redirect: 'follow', so a public stream URL that answers 301/302 to http://192.168.x.x/... or http://127.0.0.1:port/... is fetched and relayed to the browser, defeating the new SSRF guard entirely.
  Fix: Use redirect: 'manual' and loop up to N hops: on a 3xx, read Location, resolve it against the current URL, require validStreamUrl(next) (and the DNS check from the companion finding) before fetching again; return 502 if the chain exceeds the hop limit or any hop is rejected.
- **validStreamUrl never resolves hostnames, so a DNS name pointing at the LAN passes the private-address check (DNS rebinding)** — src/lib/stations.ts:84
  isPrivateAddress only matches literal IPs and 'localhost'; a hostname whose A/AAAA record is 10.0.0.1 (or that rebinds to it after validation) is accepted and the relay then reads from the LAN host. The comment on line 57 acknowledges this ('no DNS: hostnames pass').
  Fix: Add an async validateStreamTarget(url) that does `const addrs = await dns.promises.lookup(u.hostname, { all: true })` and rejects if any address is private (reuse PRIVATE_V4 / the v6 rules on addr.address); call it at station create/update (web and Subsonic handlers) and again immediately before each fetch in the stream relay, pinning the connection to the resolved address (e.g. undici Agent with a custom lookup, or fetch by IP with a Host header) so the second resolution cannot differ from the one checked.
- **/rest reads an unbounded POST body before authenticating** — src/app/rest/[...view]/route.ts:741
  requestParams() buffers the whole form body with req.text() for any POST with a form content-type, and this runs before authenticate(); /rest is outside the proxy matcher (/api/:path*), so an unauthenticated client can post multi-hundred-MB bodies that are held in memory and parsed into URLSearchParams.
  Fix: Reject early when Content-Length exceeds a small cap (e.g. 64 KiB — Subsonic form bodies are tiny) and, for chunked bodies, read the stream with a byte budget and abort past it: `const len = Number(req.headers.get('content-length')); if (len > MAX_FORM_BYTES) return subsonicError(req, 0, 'body too large', merged);` then read via req.body reader accumulating up to MAX_FORM_BYTES.
- **Public /api/health runs a synchronous full-database quick_check on every request** — src/app/api/health/route.ts:14
  PRAGMA quick_check walks every page of library.db and better-sqlite3 executes it synchronously, blocking the Node event loop; because /api/health is in PUBLIC_API with no rate limit, anyone who can reach the server can stall playback and all other requests by hammering it, with cost scaling with library size.
  Fix: Replace quick_check with a trivial probe (`getDb().prepare('SELECT 1').get()`), or keep quick_check but memoise its verdict for e.g. 60 s in a module-level variable so repeated calls return the cached result without touching the DB.
- **README does not document that TRUST_PROXY now governs X-Forwarded-Host/Proto for OAuth callback origins, nor the new X-Webhook-Token header** — README.md:280
  requestOrigin() only honours X-Forwarded-Host/Proto when TRUST_PROXY >= 1, so users behind a proxy that rewrites Host (nginx default proxy_set_header Host $proxy_host) will get Last.fm/Spotify callbacks built on the internal upstream host unless they set TRUST_PROXY; the README still describes TRUST_PROXY purely as a login-throttling knob. Line 273/308 also still say the webhook secret must be passed as ?token= although the route now prefers an X-Webhook-Token header.
  Fix: Extend the TRUST_PROXY row: 'Also lets Spotless build OAuth callback/redirect URLs from X-Forwarded-Host/X-Forwarded-Proto; set it when the proxy does not preserve the Host header.' Update the LIDARR_WEBHOOK_SECRET row and the Lidarr section to mention the X-Webhook-Token header as the preferred way to pass the secret.

## Player

- **Every store set() serialises up to 500 tracks to localStorage, including each volume-slider tick** — src/store/player.ts:189
  zustand's persist middleware calls storage.setItem (JSON.stringify of partialize(state)) synchronously on every set, and the Player's volume range input (step 0.01) calls setVolume on every onChange, so dragging the volume slider or a DJ duck/unduck serialises the whole persisted queue (up to PERSIST_MAX_TRACKS=500 Track rows, ~100-200 KB) dozens of times per second on the main thread.
  Fix: Give persist a custom `storage` whose setItem is debounced (e.g. trailing 500 ms via setTimeout, flushed on `pagehide`/`visibilitychange`), or persist the queue as ids only and resolve them on rehydrate as the review suggested. At minimum do not re-serialise the queue for volume-only changes.
- **A track that never produces its first 0.5 s is never scored or recovered by the stall logic** — src/components/Player.tsx:472
  onWaiting now returns unconditionally before any playback has happened unless the ladder is already lower than the loaded rung, and there is no timer fallback, so a fresh track (or a transcode pipe that hangs before producing data, or a restream at a new offset, whose `played` ranges are reset by the src change) that genuinely stalls at the start can sit buffering forever: Auto never calls noteStall() and the 'transcode died' restream path (which mid-track fires even when the rung is unchanged) is unreachable.
  Fix: Keep the start-of-track exemption but arm a one-shot timer on the first start-of-track `waiting` (e.g. 10-15 s): if the element is still `!paused && readyState < HAVE_FUTURE_DATA` and `played.length === 0` when it fires, treat it as a stall (noteStall() in Auto, and restream(a, target) for transcodes). Clear the timer on `playing`/`canplay`.
- **Short seeks count as listening time toward the 'played' threshold** — src/components/Player.tsx:534
  onTime adds any positive timeupdate delta <= 2 s to listenedRef, and seek() sets progress but never resets lastPosRef, so scrubbing the range slider (step 0.5 s) or the 0.5 s arrow steps on a focused slider accumulate as 'heard' seconds; a user slowly dragging through a song can trigger a history row and a Last.fm scrobble without listening.
  Fix: In `seek()` (and in `restream()` after setSrc) set `lastPosRef.current = null` so the first timeupdate after a jump is not scored; keep the delta cap as a backstop.
- **Repeat-one on a transcode replays from the pipe offset, not from the start** — src/components/Player.tsx:576
  The repeat-one branch was extended for history (resetPlayTracking + markStarted) but still restarts with `a.currentTime = 0`; after a seek on a transcode rung the element's clock is relative to `?offset=`, so position 0 is the seek point and the replay (and its new 'start'/'played' events) begins mid-song, and on an unseekable pipe the seek may not take at all.
  Fix: In the repeat-one branch, if `rungOf(a).bitrate > 0 && offsetOf(a) > 0` (or simply for any transcode), call `setSrc(a, track, rungOf(a), 0)` then play, instead of assigning currentTime.
- **A set() before Player's rehydrate effect overwrites the saved session** — src/components/Player.tsx:161
  With skipHydration the store is only rehydrated in Player's passive mount effect, but zustand persist writes partialize(get()) on every set from module load onward, so any store write that lands before that effect (a click in the paint-to-passive-effects window, or any future mount-time store call in a sibling/child component, whose effects run before Player's) first clobbers localStorage with the empty initial queue and is then itself discarded by merge (isPlaying:false, persisted queue). Today no component writes on mount, so this is latent rather than reproducible.
  Fix: Wrap the storage so writes are ignored until hydration is done: `storage: createJSONStorage(() => ({ getItem: (k) => localStorage.getItem(k), setItem: (k, v) => { if (usePlayer.persist.hasHydrated()) localStorage.setItem(k, v); }, removeItem: (k) => localStorage.removeItem(k) }))`, or move rehydrate into a useLayoutEffect / the Shell gate so it runs before any child effect.
- **DJ-ducked volume is persisted and restored at 30%** — src/lib/client/djVoice.ts:38
  duck() lowers the store volume to 30% while the DJ speaks and remembers the original only in a module variable; now that volume is persisted on every set, closing or reloading the tab mid-segue saves the ducked value and the next session comes back at 30% with no way to unduck automatically.
  Fix: Either keep ducking out of the persisted slice (e.g. a separate non-persisted `duckGain` field multiplied in the Player's effective-volume calculation) or persist `duckedFrom ?? s.volume` in partialize.

## Streaming / scanner

- **redirect: 'follow' lets a public station URL hop to a private address, bypassing the new SSRF guard** — src/app/api/stations/[id]/stream/route.ts:32
  validStreamUrl is checked only against the stored URL; the proxy then follows redirects, so a station whose public host 302s to http://127.0.0.1:port/... or a LAN address has its body relayed to any logged-in user, which is exactly what isPrivateAddress was added to prevent (admin-only input limits exposure).
  Fix: Use `redirect: 'manual'`, loop up to ~5 hops, and run `validStreamUrl(location)` on each Location header before following; 502 on a rejected hop.
- **Subsonic stream path never passes durationSec, so the fit shortcut and offset bounding do not apply to Subsonic clients** — src/app/rest/[...view]/route.ts:134
  The stated goal of the streaming fix (CHANGELOG:19, review #10-11) is to serve files that already fit maxBitRate raw, but streamTrack selects only `path`, omits durationSec, and still uses sync existsSync, so DSub/Symfonium-style requests with maxBitRate=320 always re-encode an MP3 that already fits, and timeOffset is passed to ffmpeg unbounded.
  Fix: Select `path, duration`, replace existsSync with the async stat used by /api/stream, and pass `durationSec: Number(row.duration) || 0` — after applying the offset fix above so transcodeOffset requests are never served raw from byte 0.
- **Inverted byte range returns 416 and If-Range accepts weak tags / later dates, deviating from RFC 9110** — src/lib/streaming.ts:125
  `bytes=500-100` is syntactically invalid and RFC 9110 §14.1.1 says an invalid ranges-specifier MUST be ignored (serve 200), not answered 416; §13.1.5 requires strong comparison for If-Range (a W/ tag must not match) and an exact HTTP-date match, but the code matches weak tags and any date >= mtime.
  Fix: Return null (full 200) when `start > end`; in ifRangeMatches compare dates with `===` and treat a `W/` prefixed If-Range as a non-match (or keep the deliberate leniency but note that Chrome/Firefox never send weak tags in If-Range, so it is dead code).
- **Artwork routes stat then readFile without a catch, so a concurrent scanner unlink/rewrite yields a 500 instead of the placeholder** — src/app/api/artwork/[albumId]/route.ts:53
  The scanner now removes orphan art after prune/dedupe and writeArtAtomic does rm+rename, creating windows where a file passes the stat check but is gone by readFile; the rejection propagates as an unhandled route error.
  Fix: `const buf = await fs.promises.readFile(file).catch(() => null); if (!buf) return placeholder(id);` in both artwork routes.

## Subsonic

- **transcodeOffset advertised but offset dropped on every raw-file fallback** — src/lib/streaming.ts:213
  The REST route now advertises the OpenSubsonic transcodeOffset extension and forwards timeOffset as opts.offset, but serveTrack returns the raw file from byte 0 and ignores opts.offset whenever the transcode cap is hit (line 213) or the source-fits-cap shortcut fires (line 210); offset is only applied at line 228 after those early returns.
  Fix: When opts.offset > 0, do not take the raw shortcuts: either skip the cap/fits-cap early returns (`if (offset > 0) { /* always transcode */ }`), or when forced to serve raw, compute an approximate byte start (`Math.floor(st.size * offset / durationSec)`) and respond 206 from there so the client resumes near the requested second instead of restarting at 0. At minimum apply this on the cap path, which is the one the Subsonic route (no durationSec) can hit.
- **offset/*Offset params interpolated into SQL unvalidated; non-integer value crashes the handler** — src/app/rest/[...view]/route.ts:170
  num() was hardened for size/count, but the paging offsets are still `Number(x) || 0` spliced straight into `OFFSET ${offset}`; a value such as offset=1.5 makes SQLite throw 'datatype mismatch' (verified against the installed better-sqlite3) and 1e999 becomes `OFFSET Infinity` (syntax error), so the request ends as error code 0 'internal error' instead of being clamped.
  Fix: Add an `offsetOf(q, key)` helper mirroring num(): `const v = Math.floor(Number(raw)); return Number.isFinite(v) && v > 0 ? v : 0;` and use it for every OFFSET, or bind LIMIT/OFFSET as named parameters instead of string interpolation.
- **Missing required id returns code 70 (not found) instead of 10 (missing parameter)** — src/app/rest/[...view]/route.ts:129
  Only getLyricsBySongId distinguishes an absent id (code 10) from an unknown one (code 70); stream, download, getCoverArt, getArtist, getAlbum, getSong, getMusicDirectory, getSimilarSongs and ownPlaylist all collapse `id` absent into 70, contradicting the Subsonic error table (10 = required parameter missing) that clients use to decide whether to show 'not found' or report a client bug.
  Fix: Add a tiny guard used by every id-taking handler: `const raw = ctx.q.get('id'); if (!raw) return fail(ctx, 10, 'id required');` before parseSid, keeping 70 for a well-formed id that does not resolve.
- **scrobble time accepts any positive number, so seconds-epoch values are stored as 1970 plays** — src/app/rest/[...view]/route.ts:532
  The new played_at handling rejects timestamps more than an hour in the future but has no lower bound; a client that sends `time` in seconds (a common bug, and the Subsonic spec only says 'milliseconds since 1970') passes `timeMs > 0`, produces a history row dated 1970-01-20 and a Last.fm scrobble with a 1970 timestamp that Last.fm silently ignores, whereas the prior code at least wrote played_at = now for the local history.
  Fix: Treat implausibly small values as 'no usable time' (fall back to now) or as seconds: e.g. `const ms = timeMs < 1e11 ? timeMs * 1000 : timeMs;` then apply the existing bounds, or simply require `timeMs >= 1e12` (year 2001) before trusting it.
- **recent/frequent album lists still return every album, including never-played ones** — src/app/rest/[...view]/route.ts:177
  The per-user fix adds `h.user_id = @uid` to the ORDER BY subqueries but keeps `where = '1=1'`, so getAlbumList(type=recent|frequent) pages through the whole library with unplayed albums (NULL / 0) sorted last; a client's 'Recently played' shelf therefore shows the entire collection for a profile with little history, unlike the web app's recently-played query.
  Fix: For both types also set `where = 'EXISTS (SELECT 1 FROM history h JOIN tracks ht ON ht.id = h.track_id WHERE ht.album_id = al.id AND h.user_id = @uid)'` so only albums the acting profile has played are returned.

## API / integrations

- **Trending page never shows the new error flag and renders a negative-cached empty chart as a permanent loading skeleton** — src/app/trending/page.tsx:207
  genreTrending() now returns an `error` string and countryChart() negatively caches an empty chart for 10 minutes, but the page's Data type omits `error`, nothing renders it, and `data.chart.length === 0` is treated as 'still loading', so when the chart endpoint is down the user sees a skeleton that never resolves and no explanation for missing genre rows.
  Fix: Add `error?: string` to the page's Data interface and render it (e.g. a subdued banner above the sections). Track chart reloads with an explicit `chartLoading` state instead of `chart.length === 0`, and when the chart is genuinely empty show a 'Chart unavailable right now' message rather than the skeleton. Optionally have countryChart return `{ tracks, failed }` like genreChart so the route can set `error` for the country chart too.
- **Spotify OAuth callback reports 'token exchange or import failed' for a successful connection when the taste import throws** — src/app/api/spotify/callback/route.ts:31
  Before this branch importTaste never threw on a Spotify Web API error (api() returned null). Now a 429, 403 (user not on the dev-mode allowlist) or 5xx during the first import makes the callback redirect with `spotify_error=token exchange or import failed` even though exchangeCode already stored valid tokens, so Discover shows 'Spotify connect failed' while Settings shows 'Connected' with zero artists imported.
  Fix: Separate the two steps: on exchangeCode failure keep the current error; on importTaste failure after a successful exchange redirect with `spotify=connected&spotify_warning=<message>` (e.g. 'connected, but the first import failed: HTTP 429 — use Re-import in Settings') so the user is not told the connection failed. Alternatively run the first import best-effort and log it.
- **Settings 'Re-import taste' discards the new 401/429/502 error responses, so failures are silent** — src/app/settings/page.tsx:410
  POST /api/spotify/status now returns typed JSON errors (reconnect required / rate-limit with retryAfter / HTTP 502) via spotifyErrorResponse, but the only caller ignores the response entirely and just refetches status, so a failed re-import looks like a no-op and the 'reconnect required' message is never shown.
  Fix: Read the POST response: `const res = await fetch(...); if (!res.ok) { const d = await res.json().catch(() => ({})); setSpotifyMsg({ ok: false, text: d.error ?? `Re-import failed (HTTP ${res.status})` }); }` and render it next to the buttons, mirroring the existing lidarrMsg pattern.
- **Radio limit clamp still passes a fractional limit to SQLite, which raises SQLITE_MISMATCH (500)** — src/app/api/radio/route.ts:19
  The new clamp only checks finite and > 0, so `?limit=1.5` is bound as 1.5 to `LIMIT ?`; SQLite rejects a non-integer LIMIT with 'datatype mismatch' and the route throws instead of answering (verified with better-sqlite3: `LIMIT ?` bound to 1.5 → SQLITE_MISMATCH).
  Fix: Truncate to an integer: `const limit = Number.isFinite(requested) && requested >= 1 ? Math.min(Math.floor(requested), 30) : 15;` (or `Number.isInteger(requested) && requested > 0`).
- **A 401 from the Spotify Web API does not drop the stored tokens, so status stays 'connected' while every import says 'reconnect required'** — src/lib/spotify.ts:354
  Token invalidation only happens inside tokenRequest for the refresh grant. If api() itself gets a 401 (e.g. Spotify revokes the access token or the app's credentials change), spotifyErrorResponse answers 'Spotify reconnect required' but loadTokens() still returns the dead tokens, so spotifyStatus().connected remains true, the Settings UI keeps showing Connected/Re-import instead of the Connect button, and autosync retries the dead grant daily. This contradicts the class doc '401 means the stored grant is unusable'.
  Fix: In api(), when `res.status === 401`, call `delSetting(tokensKey(userId))` (pass userId into api, or wrap the Web API call in a helper that does so) before throwing, so a 401 from either endpoint leaves the profile disconnected and the UI offers Connect again — matching the behaviour already implemented for invalid_grant.

## UI

- **Stale Deezer results linger under a newer query when the new Deezer fetch fails** — src/app/search/page.tsx:143
  The abort fix stops an older response from landing late, but `dz` is only ever replaced on success, so when the user types a new query and the Deezer proxy errors (or returns non-2xx), the previous query's "Not in your library" artists/albums/tracks stay on screen under the new query's library results; the same stale block also stays visible while `status === 'error'` hides the library results.
  Fix: Clear the Deezer block when a tick starts or fails: inside the timeout before the fetches call `setDz(null)`, and in the Deezer catch `if (!isAbortError(err)) setDz(null)`. Optionally also gate the section on `status !== 'error'`.
- **Optimistic playlist reorder is not rolled back on a non-2xx PUT** — src/app/playlist/[id]/page.tsx:99
  `reorder` applies the new order to state immediately and only re-syncs on a rejected fetch (network failure). A 404 from the new ownership check (`ownedPlaylistId` returns null → notFound), a 400, or the proxy's 401 JSON all resolve with `res.ok === false`, so the UI keeps the optimistic order and the aria-live region announces a move that never persisted; a reload silently reverts it. removeTrack/removePlaceholder call load() unconditionally, so reorder is the odd one out.
  Fix: const res = await fetch(...).catch(() => null); if (!res?.ok) load(); — i.e. refetch on any failure, not just a rejected promise.
- **Search page never renders its loading state** — src/app/search/page.tsx:211
  `status` can be 'loading' but no branch renders anything for it: arriving at /search?q=… from the TopBar (results null, status loading) shows a blank page until the API answers, and on a slow server there is no feedback at all. Every other converted page renders a skeleton for 'loading'; the task's intended contract (loading/empty/error/ready all visible) is not met here.
  Fix: Add `{status === 'loading' && !results && <RowListSkeleton count={6} />}` (import from @/components/Skeleton) so a first query shows a skeleton while subsequent queries keep the previous results.
- **Radios retry gives no feedback while refetching** — src/app/radios/page.tsx:138
  The retry button calls `load()` without resetting status, so the error alert stays on screen with no loading indicator; if the refetch fails again nothing visibly changes, and the user cannot tell the click did anything. Other pages reset to 'loading' via an attempt counter.
  Fix: onRetry={() => { setStatus('loading'); load(); }} or follow the other pages and bump an `attempt` dep on the effect.
- **getJson throws on an empty 2xx body (204 / no content)** — src/lib/http.ts:38
  Non-JSON error bodies are handled (text() then best-effort parse), but a successful response with no body — a 204, or a route that answers `new Response(null)` — makes `res.json()` throw SyntaxError, which pages map to the 'error' state. No API route returns 204 today (grep: only 304 for artwork), so this is latent, but the helper is the single fetch wrapper for the UI and will silently misreport the first endpoint that does.
  Fix: if (res.status === 204) return undefined as T; const text = await res.text(); return (text ? JSON.parse(text) : undefined) as T;
- **Library createPlaylist still trusts res.json() and navigates on failure** — src/app/library/page.tsx:101
  The page was converted to getJson for reads but the create path was left as-is: a 400 from the new `textField` validation (or the proxy's 401 JSON) yields `{ id: undefined }` and the page navigates to /playlist/undefined, and a rejected fetch is an unhandled rejection that leaves the modal closed with no feedback.
  Fix: const res = await fetch(...).catch(() => null); const d = res?.ok ? await res.json().catch(() => null) : null; setCreating(false); if (d?.id) { window.dispatchEvent(new Event('playlists-changed')); router.push(`/playlist/${d.id}`); } else { /* surface an error */ }
- **Discover's inline Lidarr handlers stick on 'busy' after a failed request** — src/app/discover/page.tsx:359
  The search page's download() was hardened (catch, res?.ok), but the two inline handlers on discover (new releases at line 353-359 and collection gaps at 436-442) still call fetch without a catch and write 'busy' back on `!res.ok`, so a 4xx/5xx leaves 'Sending…' forever and a network failure is an unhandled rejection with the same visible result.
  Fix: Route both through a shared helper like search's download(): `.catch(() => null)` on the fetch and store an `error:`/'fail' state on `!res?.ok` so the button re-enables or shows Failed.
- **rowKeys comment claims duplicates that the schema forbids** — src/components/TrackList.tsx:86
  The docblock says a playlist can hold the same song twice, but playlist_tracks has PRIMARY KEY (playlist_id, track_id) and POST uses INSERT OR IGNORE, so duplicate track rows cannot exist; the `#n` suffixing is dead code and the comment misleads anyone reading the reorder PUT (which also keys by track_id and would be lossy if duplicates were possible).
  Fix: Either reword the comment (keys guard against a track and a placeholder sharing an id space, and are defensive against future duplicates) or drop the suffixing and use `t.missing ? `p-${placeholderId}` : `t-${id}``.

## DevEx / ops

- **Shutdown handler pre-empts Next's own graceful SIGTERM drain and masks the signal exit code** — src/instrumentation.ts:27
  Next's start-server already installs SIGTERM/SIGINT handlers that `server.close()` (finish in-flight requests), close the Next server and `process.exit(143/130)`. This handler is registered later on the same signals and calls `process.exit(0)` synchronously after closing the DB, so Next's drain never completes: active stream/transcode responses are cut, any request touching the DB in that window throws 'database connection is not open', and the container exits 0 on SIGTERM. It also does not stop the scan scheduler or wait for a running scan, which the review report named as the intent.
  Fix: Do not call process.exit in the handler: checkpoint and close the DB inside a `process.once('beforeExit'|'exit')` hook or after Next's drain (e.g. register with `NEXT_MANUAL_SIG_HANDLE` semantics in mind), stop the scheduler (`clearInterval`) and let Next's cleanup own the exit code; if a hard deadline is wanted, `setTimeout(() => process.exit(143), 5000).unref()`.
- **README says CI runs `npm run format:check`, but ci.yml does not** — README.md:592
  The Development table lists format:check among the scripts and states 'CI runs all of these on every pull request', while both workflows run only typecheck, lint, test and build. CONTRIBUTING.md also admits a repo-wide format has never been run, so adding the step would currently fail.
  Fix: Change the sentence to 'CI runs typecheck, lint, tests and the production build on every pull request' (or add `npm run format:check` to ci.yml after landing a formatting commit).
- **Version bumped to 0.2.0 without a CHANGELOG entry while hard-coded version strings remain** — CHANGELOG.md:36
  package.json now reports 0.2.0 (served publicly by /api/health as `version`), but CHANGELOG.md has only `[Unreleased]` and `[0.1.0]`, so the shipped version has no changelog section. The review item this branch addresses asked to import the package version into subsonic.ts and lyrics.ts; both are still literals and lyrics.ts still announces 0.1.0 to LRCLIB.
  Fix: Either keep package.json at 0.1.0 until release or add a `## [0.2.0] - 2026-10-08` section; and replace both literals with `pkg.version` imported from package.json the way health/route.ts does.
- **BACKUP_DIR on a separate bind mount is never made writable by the entrypoint** — docker-entrypoint.sh:32
  The branch adds BACKUP_DIR so backups can 'land on a different disk/mount', but the entrypoint fixes ownership of /data only. A Docker user who mounts e.g. `./backups:/backups` (created root-owned by compose) and sets BACKUP_DIR=/backups gets an EACCES from `fs.mkdirSync(BACKUP_DIR)` on every scheduled backup, logged but never surfaced, and no backups at all.
  Fix: In the entrypoint, also fix `$BACKUP_DIR` when it is set, is a directory and lies outside /music (`[ -n "${BACKUP_DIR:-}" ] && [ -d "$BACKUP_DIR" ] && chown ... "$BACKUP_DIR" || true`), or document in the README BACKUP_DIR row that an external mount must be owned by PUID:PGID.

## AI DJ feature

- **No per-user rate limit or cost guard on DJ routes; /api/dj/speak is an open TTS proxy for the admin's key** — src/app/api/dj/speak/route.ts:14
  Any authenticated profile can call /api/dj/speak with arbitrary text (not only DJ lines), /api/dj/chat (up to 2 LLM calls + up to ~24 Deezer lookups per message), /api/dj/segue and /api/dj/transcribe in a tight loop; nothing limits requests per user, so hosted-provider credits (ElevenLabs/OpenAI/Anthropic) configured by the admin can be drained by a non-admin.
  Fix: Add a small in-memory per-user token bucket (e.g. N requests/min keyed by session userId) applied in chat, speak, segue and transcribe, returning 429 with Retry-After; optionally restrict speak to text the server produced (sign the `say` text or cache recent replies per user and only synthesize those).
- **Library tag text flows into the prompt and the model's create_playlist action writes to the DB without confirmation** — src/lib/dj/dj.ts:212
  Track titles, artist names, genres, Spotify taste and Discover names are inlined verbatim into the system prompt, and the model-chosen `create_playlist` action is executed immediately (INSERT into playlists/playlist_tracks/playlist_placeholders) for the calling user. A crafted tag in a shared library (e.g. a file pulled via Lidarr) can steer the model into creating junk playlists in every profile that chats, or into `suggest` entries whose 'Get this artist' button files Lidarr requests.
  Fix: Treat create_playlist as a proposal: return the resolved tracks/placeholders in the reply and let the page's existing 'Save as playlist' card persist them (TrackCard already does this), or require an explicit confirm round-trip. Also wrap library-derived text in clearly delimited data blocks with an instruction that it is data, not instructions.
- **Anthropic provider ignores the configurable Server URL** — src/lib/dj/llm.ts:166
  DjSettings shows an editable 'Server URL' for every LLM provider and merge() saves cfg.llm.baseUrl for Anthropic too, but completeAnthropic and the Anthropic branch of listModels construct the SDK client without baseURL, so a proxy/gateway URL the admin enters is silently ignored and traffic goes to api.anthropic.com.
  Fix: Pass `baseURL: baseUrl` (the already-computed `(cfg.llm.baseUrl || p.defaultBaseUrl)`) into both `new Anthropic({...})` calls, or hide the Server URL field when llmP.id === 'anthropic'.
- **Every chat loads the full tracks and artists tables and fetches tracks one by one** — src/lib/dj/library.ts:177
  runDj calls buildIndex() (SELECT every track joined to artists) and buildListenerProfile → requestHits (SELECT every artist, every distinct genre) on each message, then tracksByIds runs one getTrack() query per id (up to ~60). On a large library this is hundreds of ms and megabytes of allocation per message, and it duplicates playlistMatch.buildLocalIndex.
  Fix: Cache the LibraryIndex in module scope keyed on a library version (e.g. MAX(mtime)/COUNT(*) or bump on scan completion) and reuse playlistMatch.buildLocalIndex; replace tracksByIds with a single `${TRACK_SELECT} WHERE t.id IN (...)` query and reorder in memory.
- **Transcribe buffers the whole multipart body before enforcing the 10 MB cap** — src/app/api/dj/transcribe/route.ts:15
  req.formData() parses and holds the entire upload in memory before audio.size is compared to MAX_BYTES, so the 413 guard does not protect the server from a multi-hundred-MB request; Next.js route handlers impose no body limit of their own.
  Fix: Check `Number(req.headers.get('content-length'))` against MAX_BYTES (plus a small multipart overhead) and return 413 before calling req.formData(); keep the post-parse size check as a backstop.
- **Provider hostnames leak to non-admin users in error messages, and a malformed env URL throws inside the catch** — src/lib/dj/llm.ts:66
  The status route is documented as exposing 'no URLs or keys', but chat/speak/segue return LlmError/SpeechError messages verbatim, which embed the configured server host (`Could not reach host`, `HTTP 500 from host`). Separately, `new URL(url)` is evaluated inside the catch/error paths, so an invalid env value such as LMSTUDIO_URL=localhost:1234 throws a TypeError instead of a clean LlmError.
  Fix: Compute the host once outside the try (guarded) or drop it from user-facing messages for non-admins (`'The DJ server is unreachable'`), logging the detailed message server-side; validate env-provided default URLs with cleanBaseUrl at startup.
- **README claims about suggestion verification and DJ_PROVIDER default do not match the code** — README.md:555
  README says unmatched picks are shown 'only when Deezer confirms the song exists' and that DJ_PROVIDER defaults to `ollama`; the code keeps explicit `suggest` picks when Deezer is unreachable, and with DJ_PROVIDER unset the default provider is LM Studio (LLM_PROVIDERS[0]).
  Fix: Change README line 555 to say unverifiable explicit suggestions are still shown (only Deezer-rejected ones are dropped), and change the DJ_PROVIDER default in the env table to `lmstudio` (or make defaultConfig fall back to ollama to match the docs and .env.example).
- **Dead 'ollama_schema' structured-output branch: Ollama never receives the JSON schema** — src/lib/dj/llm.ts:124
  The Ollama branch only sends `format: REPLY_SCHEMA` when p.structured === 'ollama_schema', but no provider declares that value (ollama is configured as 'none'), so the schema and its retry-without-format fallback are unreachable and Ollama replies rely purely on prompt discipline.
  Fix: Set `structured: 'ollama_schema'` on the Ollama provider (Ollama's /api/chat accepts a JSON-schema `format`), or delete the variant from LlmProvider['structured'] and the branch.
- **Deezer track search and library index reimplemented instead of reusing existing code** — src/lib/dj/dj.ts:140
  deezerLookup duplicates the Deezer search already in src/app/api/preview/route.ts and the fetch helpers in discover.ts/releases.ts (each with its own timeout/error handling), and library.buildIndex duplicates playlistMatch.buildLocalIndex with slightly different normalisation (titleKey vs norm), so DJ matching and Spotify/placeholder matching can disagree on the same song.
  Fix: Extract a shared `searchDeezerTrack(artist, title)` in src/lib/deezer.ts used by preview and the DJ, and either reuse buildLocalIndex (extend WantedTrack lookups to accept title+artist only) or move titleKey into playlistMatch so both matchers agree.
- **Mic recorder and safety timer are not cleaned up on unmount; 'Get this artist' can stick on 'Adding…'** — src/app/dj/page.tsx:199
  toggleRecord stores the MediaRecorder in recorderRef and arms a 30 s setTimeout, but the unmount cleanup only pauses the preview and stops speech; navigating away while recording keeps the microphone live for up to 30 s and then runs the onstop handler, which calls send() on an unmounted page. getIt() awaits fetch with no try/catch, so a network error leaves got[k] === 'busy' permanently.

## Cross-cutting

- **Station stream proxy private-address guard is bypassable via redirect: 'follow'** — src/app/api/stations/[id]/stream/route.ts:32
  validStreamUrl() now rejects loopback/RFC1918/link-local hosts so the relay cannot be used to read LAN services, but the proxy fetches with `redirect: 'follow'` and only the original URL is validated. An admin-entered public URL (or any public host that later changes its redirect) that 302s to http://127.0.0.1:... or http://192.168.x.x:... is followed and its body is relayed, defeating the guard. The original report (docs/code-review-2026-10-07.md:84) explicitly flagged the forward 'after redirect: follow', so the fix is incomplete relative to its stated intent. Hostname-based URLs resolving to private IPs are also unchecked, which the code acknowledges ('no DNS: hostnames pass').
  Fix: Use `redirect: 'manual'` and loop (max ~5 hops) re-running `validStreamUrl(location)` on each Location before following; or at minimum, after `fetch` with follow, check `validStreamUrl(upstream.url)` and abort/502 when the final URL fails. Document in the stations.ts comment that hostnames are not resolved.
- **Two request-origin helpers with conflicting X-Forwarded-Host trust policies (proxy.ts vs auth.requestOrigin)** — src/proxy.ts:27
  The auth cluster introduced `requestOrigin()`/`trustedProxyHops()` in auth.ts that only believe X-Forwarded-Host/Proto when TRUST_PROXY is set, while proxy.ts's CSRF `sameOrigin()` still trusts X-Forwarded-Host unconditionally and ignores TRUST_PROXY. Not exploitable in practice (Sec-Fetch-Site is checked first and browsers cannot set X-Forwarded-Host without a preflight), but the codebase now documents two opposite policies for the same header, and a deployment behind a proxy that sets X-Forwarded-Host but not TRUST_PROXY gets inconsistent behaviour between CSRF checks and OAuth callback URLs.
  Fix: Export a small `expectedHost(req)` from auth.ts (reusing firstForwarded/trustedProxyHops/HOST_PATTERN) and use it in proxy.ts sameOrigin, so both places share one trust policy; or document in README's TRUST_PROXY row that the CSRF check always honours X-Forwarded-Host.
- **Constant-time string compare implemented four times across clusters** — src/lib/subsonic.ts:44
  Each isolated branch added its own timing-safe compare: subsonic.ts `safeEqual`, lidarr/webhook/route.ts `tokenMatches`, lastfm/callback/route.ts `stateMatches`, plus the inline `expected.length === actual.length && crypto.timingSafeEqual` in auth.ts verifyPassword. Same semantics (length-mismatch -> false) copied four ways; future fixes (e.g. normalising encoding) will diverge.
  Fix: Export `safeEqual(a: string, b: string): boolean` from src/lib/auth.ts (or a new src/lib/crypto.ts) and import it in subsonic.ts, lidarr/webhook/route.ts and lastfm/callback/route.ts; keep the Buffer version in verifyPassword or wrap it too.
- **TRANSCODE_MAX_ACTIVE and ALLOW_PRIVATE_STREAM_URLS are undocumented; CHANGELOG shortcut claim does not match the implemented keys** — README.md:264
  Two new, behaviour-changing env vars are read by code but absent from the README Configuration table and from the new .env.example: TRANSCODE_MAX_ACTIVE (streaming.ts; caps concurrent ffmpeg, default = CPU count, excess listeners silently get raw files) and ALLOW_PRIVATE_STREAM_URLS (stations.ts; the only way to keep a LAN icecast station working after this upgrade, so existing users with 192.168.x stations will see 'station not found' with no documented remedy). CHANGELOG also claims 'Keyboard shortcuts for play/pause, next, previous, seek and volume' but the Player implements Space, Shift+Arrow (next/prev), Arrow (seek), M (mute toggle) and / (search focus); there is no volume up/down and README has no shortcuts section at all.
  Fix: Add rows to README's Configuration table and entries to .env.example: `TRANSCODE_MAX_ACTIVE` (default: CPU count; extra listeners get the raw file) and `ALLOW_PRIVATE_STREAM_URLS` (default off; set to 1 to allow LAN/loopback station URLs). Add a short 'Keyboard shortcuts' list to README (Space, ←/→ seek 5s, Shift+←/→ prev/next, M mute, / search) and reword the CHANGELOG line to match ('seek, mute and search').
- **Health probe runs PRAGMA quick_check (full database scan) every 30 seconds against a 5s timeout** — src/app/api/health/route.ts:14
  The Dockerfile HEALTHCHECK calls /api/health every 30s with timeout=5s and retries=3; the route runs `PRAGMA quick_check`, which reads every page of library.db. On a large library DB stored on slow/network storage this can approach or exceed 5s, flipping the container to unhealthy (and getting it restarted by Watchtower/compose policies) even though the service is fine. The README/CHANGELOG describe the endpoint as answering 503 only 'when the database is unreachable', which a cheap probe would satisfy.
  Fix: Use a constant-time probe for liveness, e.g. `getDb().prepare('SELECT 1').get()` or `pragma('user_version')`, and leave `quick_check` to the backup job where it already runs; or gate quick_check behind `?deep=1` for manual use.

## AI DJ feature — reviewer summary

AI DJ feature review (src/lib/dj, src/app/api/dj, src/app/api/settings/dj, src/app/dj, DjBooth/DjSettings, djVoice, dj-test, docker-compose.voice.yml). The security basics hold: GET /api/settings/dj returns only keySet booleans (publicConfig), keys never reach the browser, nothing in the DJ code logs keys, LLM output is only rendered as React text (no dangerouslySetInnerHTML/eval/shell/paths) and every DB write is parameterised; all /api/dj/* routes sit behind the proxy session check plus explicit currentUserFrom checks; no LAN IPs or personal paths are hard-coded (the override example uses placeholder 192.168.1.10/nas.local and is gitignored). Anthropic SDK usage (claude-opus-5-5/sonnet-5-5/haiku-4-5 ids, server-side-fallback-2026-07-01 + fallbacks:'default', output_config.effort, refusal stop reason, ms timeout) checks out against the current API. What a maintainer should fix first: (1) no per-user rate limit or cost guard on chat/speak/segue/transcribe, so any profile can spend the admin's hosted-provider credits and use /api/dj/speak as a free TTS API; (2) library tag text is inlined into the prompt and the model's create_playlist action writes to the DB with no confirmation, so a crafted tag can create playlists in every chatting profile; (3) the Anthropic provider silently ignores the editable Server URL; (4) every chat loads the whole tracks and artists tables plus an N+1 getTrack loop. Remaining findings are edge-case correctness (transcribe buffers the whole upload before the 10 MB check, provider hostnames leak in error messages, a dead ollama_schema branch), client cleanup gaps (mic recorder/timer not cleared on unmount, getIt stuck on network error), duplication with the existing Deezer and local-index code, and README claims that the code does not match.

## Rejected by the verifier

- Admin-configurable provider URLs allow the server to be pointed at any http(s) host (SSRF by design) — This is intended behavior, not a defect: all three handlers in src/app/api/settings/dj/route.ts (lines 71, 77, 89) call requireAdmin, which admits only ADMIN_USER_ID (src/lib/user.ts:91-96), i.e. the self-hosting operator who already controls the server. Pointing the server at LAN/localhost hosts is the documented primary use case (README:275 LMSTUDIO_URL/OLLAMA_URL defaults, README:545 'Serve on Local Network'), so rejecting internal ranges in cleanBaseUrl (config.ts:196-205) would break the product; the POST 'models'/'test' actions using unsaved form values are the explicit 'Load models' / 'Test model' flow (README:545). The finding itself concedes it is acceptable and proposes only a doc note, which is not a security finding.
